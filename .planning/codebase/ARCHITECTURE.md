# Architecture

**Analysis Date:** 2026-11-04

The public website is a fully static build with no server runtime (`astro.config.mjs`: "Hostinger shared hosting has no server runtime"). All dynamic behavior (placement test, bookings, applications, staff admin) lives in a separate Cloudflare Worker that the static pages call over HTTP.

## Pattern Overview

**Overall:** Static multi-page site (Astro SSG, directory output) with a split-out serverless API (Cloudflare Worker + D1) for interactive features.

**Key Characteristics:**
- Zero client framework: pages are `.astro` files; interactivity is inline `<script>` blocks in components (e.g., `src/pages/[lang]/placement-test/index.astro` step tracker, dispatching `placement:started` / `placement:done` DOM events).
- One route file serves both locales: `src/pages/[lang]/...` with `getStaticPaths = localePaths` generating `/en/` and `/ar/` builds (`src/i18n/pages.ts`). Only legal pages still have per-locale files (`src/pages/en/legal/*`, `src/pages/ar/legal/*`).
- Locale-specific strings are plain objects, resolved at build time (`src/i18n/ui.ts`, `src/i18n/pages.ts`). No i18n runtime library.
- Content is typed via Astro content collections with zod schemas (`src/content.config.ts`): `courses` (`category` enum kids/adults/women/business/exam-prep) and `blog`. Each locale is a separate tree under `src/content/<collection>/{en,ar}/`.
- Structured data (JSON-LD) is generated by code, never a plugin: `src/lib/schema.ts` builders are passed to `Layout` via the `jsonLd` prop.
- Reviews are fetched at build time from Google (`src/lib/googleReviews.ts`), so no staff-editable testimonial path exists.
- Staff-only pages are excluded from the sitemap (`astro.config.mjs` sitemap `filter`) and marked `noindex` via the `Layout` prop.

## Layers

**Presentation layer (static pages and layout):**
- Purpose: Render all public pages, both locales, at build time.
- Location: `src/pages/`, `src/layouts/Layout.astro`, `src/components/*.astro`
- Contains: Route `.astro` files, shared chrome (`Header.astro`, `Footer.astro`, `WhatsAppButton.astro`, `ConsentBanner.astro`, `ConsentHead.astro`), page-level experience components (`HomeExperience.astro`, `CourseCard.astro`, `RegistrationExperience.astro`, etc.).
- Depends on: `src/i18n/*`, `src/lib/*`, `astro:content` collections, `src/styles/*`.
- Used by: Browser (static HTML).

**Content layer:**
- Purpose: Course and blog data as validated Markdown.
- Location: `src/content/courses/{en,ar}/*.md`, `src/content/blog/{en,ar}/*.md`, schema in `src/content.config.ts`.
- Contains: Frontmatter only (price, schedule, FAQs, intake dates, etc.). Courses use structured FAQ arrays so FAQ accordion and FAQPage schema come from one source.
- Depends on: Nothing at runtime.
- Used by: `src/pages/[lang]/courses/[slug].astro`, `src/pages/[lang]/courses/index.astro`, `src/pages/[lang]/blog/*`, `src/pages/[lang]/search-index.json.ts`.

**Client API layer (browser → worker):**
- Purpose: Typed fetch wrappers for the placement API.
- Location: `src/lib/placementApi.ts`
- Contains: `startSession`, `submitAnswer`, `listSlots`, `createBooking` and shared payload types (`QuestionPayload`, `DonePayload`). The base URL comes from `import.meta.env.PUBLIC_PLACEMENT_API_URL`. Requests use `credentials: 'include'` for the admin cookie/session.
- Used by: `src/components/placement-test/TestRunner.astro`, `RegistrationForm.astro`, `ResultBooking.astro`, `AdminPanel.astro`, `ApplicationForm.astro`.

**API layer (Cloudflare Worker):**
- Purpose: Stateful test sessions, scoring, bookings, applications, admin.
- Location: `placement-test-worker/src/`
- Contains:
  - `index.ts`: Hand-rolled router. A `ROUTES` table of `{ method, pattern, admin?, handler }`; `:param` segments are positional. Admin routes are gated by `requireAdmin` before the handler runs. CORS is applied to every response via `withCors`. Only `https://elc.com.sa` is allowed, plus loopback origins when `LOCAL_DEV === 'true'`.
  - `routes/session.ts` (start session, answer), `routes/booking.ts` (list slots, create booking), `routes/admin.ts` (login, slots, bookings, questions), `routes/application.ts` (submit and manage student applications).
  - `auth.ts` (admin session), `scoring.ts` and `bands.ts` (level placement), `kids.ts` (kids-track rules and question-ID constants), `db.ts` (D1 queries), `types.ts` (`Env`, row types).
  - `test-utils/fakeD1.ts` for tests.
- Depends on: Cloudflare D1 binding `DB` (`placement-test-worker/wrangler.toml`), `ADMIN_SESSION_TTL_SECONDS` var.
- Used by: The placement test and application UI through `src/lib/placementApi.ts`.

**CMS auth layer:**
- Purpose: GitHub OAuth code-to-token exchange for Decap CMS (`/admin`, built into `dist/admin/`).
- Location: `cms-oauth-worker/src/index.js`, config in `cms-oauth-worker/wrangler.toml`. The static admin page is `public/admin/` (copied to `dist/admin/`).
- Secrets are set with `wrangler secret put` and never stored in the repo.

## Data Flow

### Primary Request Path (static page)

1. Request for `/{en|ar}/...` is served from `dist/` as a prebuilt HTML file (`astro.config.mjs` `format: 'directory'`).
2. Page imports its content through `astro:content` and dictionary helpers, e.g. `src/pages/[lang]/courses/[slug].astro`.
3. `Layout.astro` composes head metadata, hreflang, JSON-LD, consent head, header/footer, and the WhatsApp button.

### Placement Test Path (runtime)

1. `src/components/placement-test/RegistrationForm.astro` collects name, phone, DOB and track, then calls `startSession()` in `src/lib/placementApi.ts`.
2. `POST /api/session` is routed in `placement-test-worker/src/index.ts` to `handleStartSession` in `routes/session.ts`, which creates a row in D1 via `db.ts`.
3. `TestRunner.astro` loops: receives a `QuestionPayload`, posts an answer via `submitAnswer()`, and the worker's `handleAnswer` grades it (`scoring.ts`, `kids.ts`) and returns the next question or a `DonePayload` with `level`/`levelName`.
4. Progress is announced by DOM events `placement:started` and `placement:done`; `src/pages/[lang]/placement-test/index.astro` listens to advance the step indicator.
5. `ResultBooking.astro` calls `listSlots()` then `createBooking()`. A 409 response is a normal "slot filled" outcome.

### Admin Path

1. Staff open `src/pages/en/placement-test/admin.astro` (`noindex`, excluded from sitemap). It mounts `src/components/placement-test/AdminPanel.astro`.
2. `POST /api/admin/login` sets a session; every `/api/admin/*` route passes through `requireAdmin` (`auth.ts`) with TTL 43200 seconds.

### Build-Time Data Path

1. `src/lib/googleReviews.ts` fetches reviews during `astro build`. The result feeds `organizationSchema` / `aggregateRating` in `src/lib/schema.ts`.
2. `src/pages/[lang]/search-index.json.ts` emits a search index consumed by `src/components/SearchOverlay.astro`.

**State Management:**
- Static site: none beyond DOM state in inline scripts.
- Placement test: server-side session rows in D1 (`sessions` / `current question` tracking, see migrations `0014_track_current_question.sql`); the client holds only `sessionId`.
- Consent: `ConsentBanner.astro` / `ConsentHead.astro`.

## Key Abstractions

**Locale-aware route:**
- Purpose: One source file per page for both languages.
- Examples: `src/pages/[lang]/about.astro`, `src/pages/[lang]/register.astro`
- Pattern: `export const getStaticPaths = localePaths;` plus `meta(key, locale)` and `trail(locale, [...])` from `src/i18n/pages.ts`.

**Dictionary translator:**
- Purpose: Resolve UI strings per locale at build time.
- Examples: `src/i18n/ui.ts` (`useTranslations(locale)` returns `t('placementTest.heading')`-style lookups)
- Pattern: Dotted keys into plain `ui` objects keyed by `en` / `ar`. `localeDir` gives `ltr` / `rtl`.

**Route table (worker):**
- Purpose: Declarative endpoint registration without a framework.
- Examples: `placement-test-worker/src/index.ts` (`ROUTES`, `matchRoute`)
- Pattern: Add a route by appending an object to `ROUTES` with a handler from `routes/*.ts`. Set `admin: true` to require auth.

**Question bank / track model:**
- Purpose: Kids and adults tests use fixed, sequential question IDs and band-based scoring.
- Examples: `placement-test-worker/src/kids.ts` (`KIDS_CAPITAL_QUESTION_IDS`), `scoring.ts`, `bands.ts`, migrations `0006_fixed_sequential_order.sql`, `0007_elc_level_ladders.sql`.
- Pattern: Questions live in D1 (`questions`, `passages` tables); seed data is added by numbered SQL migrations in `placement-test-worker/migrations/`.

## Entry Points

**Website build:**
- Location: `astro.config.mjs`, `package.json` scripts `dev`, `build`, `preview`.
- Triggers: `npm run build` (static output to `dist/`).
- Responsibilities: Generate all `/en/` and `/ar/` pages, sitemap, redirects (`/` to `/en/`).

**Placement API worker:**
- Location: `placement-test-worker/src/index.ts` (`export default { fetch }`), config `placement-test-worker/wrangler.toml`.
- Triggers: HTTP requests from the static site to `PUBLIC_PLACEMENT_API_URL`.
- Responsibilities: Routing, CORS, admin gating, error envelope (`{ error }`, 500 with `internal_error` outside local dev).

**CMS OAuth worker:**
- Location: `cms-oauth-worker/src/index.js`
- Triggers: Decap CMS login flow at `/admin`.
- Responsibilities: GitHub OAuth code exchange only.

**CI / deploy:**
- Location: `.github/workflows/ci.yml`, `.github/workflows/deploy.yml`
- Triggers: Deploy job is `workflow_dispatch` only; push/schedule/repository_dispatch triggers are commented out until Hostinger FTP secrets exist.

## Architectural Constraints

- **Threading:** Build is single-process Astro/Vite. Worker runs single-request-per-invocation on Cloudflare; no shared in-memory state is relied on.
- **Global state:** Module-level constants only (e.g., `ALLOWED_ORIGINS` in `placement-test-worker/src/index.ts`, `SITE` in `src/i18n/pages.ts`). No singletons with mutable state were identified.
- **Circular imports:** None observed among `src/i18n`, `src/lib`, and `src/components`. `src/i18n/pages.ts` imports from `src/i18n/ui.ts` only.
- **Static-only hosting:** The public site cannot use Astro SSR adapters or server redirects (`astro.config.mjs` comment), so anything needing a server goes in a worker.
- **Two Cloudflare workers, one D1 DB:** Worker config is per directory, so changes to `placement-test-worker` deploy independently of the site.
- **Local dev origin:** CORS only allows loopback origins when `LOCAL_DEV=true`. Do not change that gating.

## Anti-Patterns

### Hardcoded WhatsApp and phone numbers in multiple places

**What happens:** The WhatsApp number `966546656000` is hard-coded in `src/pages/[lang]/placement-test/index.astro` and again in `src/components/WhatsAppButton.astro`. Organization phone numbers are repeated in `src/lib/schema.ts`.
**Why it's wrong:** A number change requires editing several files, and the JSON-LD and visible UI can drift.
**Do this instead:** Centralize contact constants in one module under `src/lib/` and import them into `schema.ts`, the placement page, and `WhatsAppButton.astro`.

### Duplicate rule logic on client and server

**What happens:** Track and skip rules are mirrored between `src/lib/placementApi.ts` types and `placement-test-worker/src/kids.ts` / `scoring.ts`.
**Why it's wrong:** Client display logic (for example, `skipAvailable`) can diverge from server grading.
**Do this instead:** Let the worker be the single source for rules; the client should render only fields the API returns (`skipAvailable`, `correct`).

## Error Handling

**Strategy:** Worker returns JSON error bodies with explicit status codes; client treats expected non-OK statuses as data.

**Patterns:**
- `placement-test-worker/src/index.ts` wraps route handling in try/catch, logs with `console.error`, and returns `{ error }` with status 500 (message exposed only when `LOCAL_DEV === 'true'`).
- `src/lib/placementApi.ts` `request()` throws on non-OK unless the status is listed in `expectedErrors` (used for meaningful 409 booking responses).

## Cross-Cutting Concerns

**Logging:** `console.error` in the worker; no client logging framework detected.
**Validation:** Content frontmatter validated by zod (`src/content.config.ts`); API inputs validated inside route handlers in `placement-test-worker/src/routes/*.ts`.
**Authentication:** Staff admin uses a session cookie checked by `requireAdmin` in `placement-test-worker/src/auth.ts`. CMS editors authenticate with GitHub through `cms-oauth-worker`.
